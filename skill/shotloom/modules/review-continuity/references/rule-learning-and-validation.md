# Evidence-bounded learning and rule maintenance

Use only for authorized reusable learning or skill repair, not as extra paperwork for ordinary media review. Reuse the existing project feedback record and its scope; do not create a failure ticket for a general improvement without an actual failure.

## Keep evidence states distinct

- **Source proposal:** a repository rule, tutorial, imagined example or newly composed repair. Useful for hypothesis/design, not evidence that a model produced the desired result.
- **Local document/code check:** links, schemas, consistency or regression tests passed. State exactly what was checked; this cannot validate acting, sound, impact, scale or commercial performance.
- **Observed result:** identify the actual source version, model/interface, relevant settings/references, inspected time range and observed dimension. Picture-only inspection does not validate sound; a still does not validate motion.
- **Scoped working method:** adequate relevant results support reuse under stated conditions, with known failures and untested transfers retained. One successful take is local evidence, not a universal success rate or proof across models/styles.

These labels describe evidence in maintenance/handoff, not mandatory prompt text or proprietary adapter fields. They do not replace existing platform evidence levels.

## Learning from model-and-prompt cases

Before attributing a result to wording, pair exact model **and variant**, host, input mode, real bound source roles/order, prompt version, settings and corresponding output. The generation skill's [manual authority index](../../generation/references/model-manual-authority.md) separates official syntax/recommendations from host limits and external examples. A mutable canvas field is not an immutable submission log; absent model or inconsistent durations leave attribution unresolved.

Distinguish design carried by an image, action/camera carried by a video, and instructions carried by text. Compare like tasks within a model/mode before proposing a wording lesson. Different genres, inputs and selection histories confound a model ranking; attractive survivors do not reveal failed attempts. Record the portable creative relationship separately from model-specific expression. Transfer across models remains a proposal until tested with the target model and comparable controls. Do not label a short Kling frame prompt a universal rule for H3, or a Seedance 2.5/Mini case evidence for full 2.0. Reused still-frame evidence supports only the visible composition/state, not impact, timing or audio.

## Model-selection feedback

When authorized learning includes model choice, use the [selection contract](../../generation/references/video-model-selection.md) and [dated profiles](../../generation/references/video-model-profiles.md). Compare expected advantage and risk against actual passed/failed/unverified requirements; also record unexpected findings. Keep the selection snapshot/source versions, exact variant/mode/host, references and prompt/settings, output path/hash, inspected interval/dimensions, cumulative attempts and known actual expense in the existing authorized record. Missing attempt denominators do not support a success rate or accepted-clip cost estimate.

Distinguish a functional input/control limit, a host limitation, faulty compilation, stochastic execution and a failed creative design before generalizing. One accepted result may become a scoped observed result, not a global model ranking. Conflicting evidence narrows the applicable conditions; retain counterexamples. Ordinary reviews do not edit the shared profile, create a new ticket or run a paid A/B test. Only a separately authorized maintenance scope may promote/revise a reusable observation, and it never substitutes for current official grammar or widens the permitted model pool.

Bind style-related feedback to the actual appearance contract/version and, for mixed work, the inspected layer/interval. Record allowed variation and which visual/temporal dimensions were actually reviewed; a broad 2D/3D label is not enough to transfer the result. A new style can retain applicable input/control knowledge while leaving its output appearance unverified. A desk test that changes style names or a schema pass is not a cross-style production benchmark.

## Before promoting a repair to a rule

Name the failure it addresses, causal hypothesis, relevant scope, invariants, expected observable improvement and stopping condition. Keep competing explanations open when source/prompt/media evidence is incomplete. Prefer a scoped positive instruction, control change or diagnostic branch over a global banned word, cast limit or timing formula inferred from one failure.

Read the rule alongside its legitimate countercase: stillness can be acting; simultaneous attacks can be readable; giant imagery can be flat 2D; a story can end unresolved or without a reversal. Define what would falsify or narrow the proposed rule. New examples may illustrate the proposal but must remain labeled untested for model execution until actual evidence exists. Do not fabricate an experiment or spend credits merely to fill that label.

## Propagate a real change, not duplicate rules

Inspect affected callers: entry routing, authoritative reference, examples/templates, compiler guidance, validator diagnostics and tests. Change only actual dependencies. Update or explicitly retire incompatible examples and automatic repair advice; do not leave an old suggested fix active after its underlying rule was withdrawn. A keyword scan can locate candidates, but a historical warning or legitimate exception must not be rejected simply for containing the same words.

Keep one authoritative home for the decision and link conditional consumers to it. Preserve the chosen style, story, sound ownership, asset approval and paid-attempt boundaries. Publicly readable external material is not automatically licensed for code/text copying; record provenance and use independently expressed methods when permission to reuse expressive content is absent or unclear.

## Proportionate validation and release

Preserve recoverable versions before editing and avoid overwriting concurrent work. Check changed files, local links, applicable schemas and affected existing tests. For behavior rules, also walk through realistic in-scope cases and nearby valid countercases; report this as a desk review unless an actual independent execution occurred. Do not add heading/keyword assertions and present their passing as semantic proof.

When a checker changes, test the observable result on valid and invalid inputs, including legitimate exceptions; run new/changed code locally within authorization. Keep automated structural findings separate from human/agent creative review and actual-media evidence. A package-existence check proves neither workflow correctness nor production quality.

Release with the change scope/version, checks and limitations, rollback path and activation conditions in the authorized maintenance record. A general skill improvement does not resolve a production ticket, reset attempts, unlock a paused task, authorize a paid trial or trigger a full re-render. Future real-use evidence can narrow or retire the rule; do not automatically generalize a project's accepted exception.
